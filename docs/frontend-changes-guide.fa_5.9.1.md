# راهنمای قابلیت‌های جدید نوبتیکس

نسخه مستند: ۱۴۰۵/۰۹/۰۱

این سند برای برنامه‌نویس فرانت‌اند تهیه شده و قرارداد استفاده از قابلیت‌های جدید را توضیح می‌دهد. مواردی که فقط برای استانداردسازی اکشن‌های قدیمی اضافه شده‌اند، در این سند نیامده‌اند.

## فهرست قابلیت‌ها

- مدیریت دسته‌بندی هزینه‌ها
- ثبت و مدیریت هزینه‌های متخصص یا مجموعه
- کنترل مالکیت و جلوگیری از دسترسی به اطلاعات مالک دیگر
- بررسی وجود اشتراک فعال و ظرفیت اشتراک
- تنظیمات تسویه مجموعه و سهم متخصص
- کال‌بک مشترک پرداخت زرین‌پال برای اشتراک و پرداخت رزرو
- پاسخ یکسان و قابل استفاده برای صفحه `/payment/callback`

## ۱. مدیریت هزینه‌ها

### هدف

این بخش برای ثبت هزینه‌های متخصص مستقل یا مجموعه طراحی شده است. هر هزینه به یک مالک از جدول `Workers` متصل است؛ بنابراین برای سالن جدول جداگانه‌ای ساخته نشده و `OwnerWorkerID` می‌تواند شناسه متخصص یا شناسه مجموعه باشد.

### موجودیت‌ها

#### `ExpenseCategory`

دسته‌بندی هزینه است.

| فیلد | کاربرد |
| --- | --- |
| `id` | شناسه دسته‌بندی |
| `name` | نام دسته‌بندی |
| `ownerWorkerID` | مالک اختصاصی؛ مقدار `null` یعنی عمومی |
| `createdByPersonID` | شخص ایجادکننده؛ برای دسته‌های پیش‌فرض سیستمی `null` است |
| `isActive` | فعال یا غیرفعال بودن |
| `description` | توضیحات |

#### `Expense`

رکورد واقعی هزینه است.

| فیلد | کاربرد |
| --- | --- |
| `id` | شناسه هزینه |
| `ownerWorkerID` | مالک هزینه؛ متخصص یا مجموعه |
| `expenseCategoryID` | شناسه دسته‌بندی |
| `title` | عنوان هزینه |
| `amountIRR` | مبلغ به ریال و عدد صحیح مثبت |
| `expenseDate` | تاریخ انجام هزینه |
| `createdByPersonID` | شخص ثبت‌کننده |
| `description` | توضیحات اختیاری |
| `isActive` | وضعیت رکورد |

### دسته‌بندی‌های پیش‌فرض

پس از اجرای Migration این دسته‌های عمومی ایجاد می‌شوند:

- اجاره محل
- حقوق و دستمزد
- مواد مصرفی
- آب، برق و گاز
- خرید تجهیزات
- تعمیرات و نگهداری
- تبلیغات و بازاریابی
- سایر هزینه‌ها

### قواعد مالکیت

- دسته عمومی (`ownerWorkerID = null`) برای مشاهده همه قابل استفاده است.
- دسته اختصاصی فقط برای مالک خودش قابل مشاهده و استفاده است.
- متخصص نمی‌تواند برای مالک دیگری هزینه ثبت یا ویرایش کند.
- متخصص زیرمجموعه نمی‌تواند هزینه‌های مجموعه را تغییر دهد.
- مدیر سیستم می‌تواند برای هر مالک هزینه یا دسته ثبت کند.
- دسته عمومی فقط توسط مدیر سیستم ایجاد می‌شود.
- دسته‌ای که قبلاً در هزینه استفاده شده باشد حذف فیزیکی نمی‌شود و API پیام خطا می‌دهد؛ در این حالت باید آن را غیرفعال کرد.
- حذف هزینه فیزیکی است و حذف نرم برای `Expense` وجود ندارد.
- نام دسته قبل از ذخیره Trim می‌شود و برای یک مالک تکراری نیست.

## ۲. API دسته‌بندی هزینه

مسیر پایه:

```text
/ExpenseCategory
```

### دریافت فهرست

```text
POST /ExpenseCategory/GetAllExpenseCategories_Base
```

نمونه ورودی:

```json
{
  "pageIndex": 1,
  "pageSize": 20,
  "searchText": "",
  "sortQuery": "name-asc",
  "ownerWorkerID": 0,
  "includeInactive": false
}
```

`ownerWorkerID=0` یعنی فرانت شناسه پروفایل جاری را ارسال نکرده و بک‌اند از پروفایل فعال کاربر استفاده می‌کند. دسته‌های عمومی نیز در پاسخ برمی‌گردند.

### دریافت تکی

```text
POST /ExpenseCategory/GetExpenseCategoryById_Base
```

```json
{ "id": 12 }
```

### بررسی وجود

```text
POST /ExpenseCategory/ExistExpenseCategory_Base
```

```json
{ "id": 12 }
```

### افزودن

```text
POST /ExpenseCategory/AddExpenseCategory_Base
```

دسته اختصاصی:

```json
{
  "ownerWorkerID": 10145,
  "name": "مواد رنگ و دکلره",
  "isActive": true,
  "description": "مواد مصرفی تخصصی"
}
```

دسته عمومی فقط توسط Admin قابل افزودن است:

```json
{
  "ownerWorkerID": null,
  "name": "هزینه متفرقه",
  "isActive": true
}
```

### ویرایش

```text
PUT /ExpenseCategory/EditExpenseCategory_Base
```

```json
{
  "id": 12,
  "ownerWorkerID": 10145,
  "name": "مواد رنگ و دکلره",
  "isActive": false,
  "description": "این دسته دیگر برای هزینه جدید استفاده نشود"
}
```

برای غیرفعال‌کردن دسته از همین اکشن استفاده شود؛ حذف دسته‌ای که سابقه دارد مجاز نیست.

### حذف

```text
DELETE /ExpenseCategory/DeleteExpenseCategory_Base
```

```json
{ "id": 12 }
```

در صورت استفاده‌شدن دسته، پاسخ `400` با پیام خطا برمی‌گردد.

## ۴. اشتراک فعال، ظرفیت و تسویه

### بررسی اشتراک فعال

برای بررسی اینکه یک متخصص یا مجموعه در لحظه اشتراک فعال دارد، از اکشن زیر استفاده شود:

```text
POST /BusinessSubscription/ExistBusinessSubscription_Base
```

```json
{ "id": 10159 }
```

شناسه ورودی `id` همان `BusinessID` است؛ یعنی شناسه رکورد متخصص یا مجموعه در جدول `Workers`. پاسخ موفق یعنی در بازه زمانی فعلی رکورد اشتراک با وضعیت `active` وجود دارد:

```json
{
  "status": true,
  "id": 10159,
  "errorMessage": ""
}
```

این اکشن فقط وضعیت وجود اشتراک را اعلام می‌کند و اطلاعات مالی سایر حساب‌ها را افشا نمی‌کند.

### ظرفیت اشتراک

فیلدهای `PlanType` و `MaxMemberCount` روی `SubscriptionPlans` نوع اشتراک و ظرفیت آن را مشخص می‌کنند. هنگام خرید، مقدارهای مهم پلن در `BusinessSubscriptions` به‌صورت Snapshot ذخیره می‌شوند تا ویرایش بعدی پلن، قرارداد قبلی را تغییر ندهد.

درصد ظرفیت مصرف‌شده فقط با شمارش متخصصان واجد شرایط محاسبه می‌شود؛ صرفاً فعال‌بودن نوبت‌دهی اینترنتی معیار مصرف ظرفیت نیست. عضویت متخصص باید به مجموعه معتبر باشد، حساب مجاز و شخص فعال داشته باشد و در همان مجموعه ارائه‌دهنده خدمت محسوب شود.

### تنظیم تسویه مجموعه

در تنظیمات مالی مجموعه، `SettlementDestination` دو مقدار دارد:

| مقدار | کاربرد |
| --- | --- |
| `Business` | کل مبلغ قابل تسویه به حساب مجموعه اختصاص می‌یابد و تقسیم داخلی با مجموعه است |
| `Separate` | سهم مجموعه و سهم متخصص جداگانه محاسبه می‌شود |

در حالت `Separate`، درصد سهم هر متخصص از `WorkerBillingSettings.RevenueSharePercent` خوانده می‌شود. اگر درصد متخصص ثبت نشده باشد، سهم مجموعه صفر و کل مبلغ متعلق به متخصص خواهد بود.

نمونه تنظیم سهم متخصص:

```json
{
  "businessID": 10144,
  "workerID": 10145,
  "revenueSharePercent": 20
}
```

در این مثال ۲۰ درصد مبلغ خدمت سهم مجموعه و ۸۰ درصد سهم متخصص است. محاسبه بر مبلغ خدمت پس از تخفیف انجام می‌شود.

### نکات نمایش مالی

- `BillingAccount` با `WorkerID` شناسه حساب مالی پلتفرم است و خودِ شناسه متخصص نیست.
- متخصص نباید اطلاعات حساب مالی مجموعه یا سایر متخصصان را مشاهده کند.
- مدیر مجموعه فقط طبق سطح دسترسی و مالکیت مجاز می‌تواند تنظیمات مجموعه و سهم اعضا را تغییر دهد.
- مقادیر درصدی در بازه صفر تا صد اعتبارسنجی می‌شوند.

## ۵. قرارداد کال‌بک پرداخت

### جریان پرداخت

1. فرانت‌اند `RequestPayment` را با `paymentID` فراخوانی می‌کند.
2. بک‌اند یک `PaymentHistory` برای تلاش پرداخت می‌سازد.
3. آدرس کال‌بک درگاه به API تأیید پرداخت اشاره می‌کند.
4. درگاه پارامترهای خود مانند `Authority` و `Status` را به API می‌فرستد.
5. بک‌اند مبلغ، شناسه تلاش، درگاه و وضعیت تراکنش را بررسی می‌کند.
6. پس از تأیید، نوع پرداخت از دیتابیس مشخص می‌شود:
   - `subscription`: خرید اشتراک
   - `service`: پرداخت رزرو مشتری
7. در حالت کال‌بک مرورگر، بک‌اند فقط نتیجه پاک‌شده را به صفحه زیر Redirect می‌کند:

```text
https://nobatix.com/payment/callback
```

`Authority` و `paymentToken` نباید در اختیار منطق فرانت‌اند قرار بگیرند.

### پاسخ JSON تأیید موفق اشتراک

```json
{
  "status": true,
  "success": true,
  "paymentVerified": true,
  "paymentHistoryId": 23,
  "paymentId": 7,
  "purpose": "subscription",
  "profileType": "Worker",
  "bookingIds": [],
  "transactionCode": "123456789",
  "resultPath": "/worker/billing/payments/result",
  "errorMessage": null
}
```

برای اشتراک سالن مقدار `profileType` برابر `Workshop` و مسیر نتیجه برابر زیر است:

```text
/workshop/billing/payments/result
```

### پاسخ JSON تأیید موفق پرداخت رزرو

```json
{
  "status": true,
  "success": true,
  "paymentVerified": true,
  "paymentHistoryId": 31,
  "paymentId": 12,
  "purpose": "service",
  "profileType": "Customer",
  "bookingIds": [101, 102],
  "transactionCode": "987654321",
  "resultPath": null,
  "errorMessage": null
}
```

### پرداخت ناموفق

در پرداخت ناموفق `status`، `success` و `paymentVerified` برابر `false` هستند و متن خطا در `errorMessage` قرار می‌گیرد. فرانت‌اند نباید فقط بر اساس وجود `paymentId` پرداخت را موفق فرض کند.

### رفتار در Refresh یا کال‌بک تکراری

کال‌بک تکراری نباید باعث ثبت دوباره شود. بک‌اند از `PaymentHistory.PaymentStatus` و تراکنش مالی استفاده می‌کند و نتیجه تأیید قبلی را برمی‌گرداند. فرانت‌اند باید صفحه نتیجه را برای Refresh ایمن طراحی کند.

## ۶. نکات پیاده‌سازی فرانت‌اند

- شناسه‌های `WorkerID` و `OwnerWorkerID` را با پروفایل فعال هماهنگ کنید.
- مبلغ هزینه را در UI به تومان نمایش دهید، اما در API با `amountIRR` و واحد ریال ارسال کنید.
- برای فهرست دسته‌ها، دسته‌های عمومی و دسته‌های اختصاصی مالک را نمایش دهید.
- دسته غیرفعال را برای ثبت هزینه جدید قابل انتخاب نکنید، ولی اگر در سابقه هزینه وجود دارد نام آن را نمایش دهید.
- خطای `400` را به‌صورت متن `errorMessage` نمایش دهید.
- پاسخ‌های صفحه‌بندی دارای `totalCount`، `pageCount` و `results` هستند.
- در صفحه کال‌بک، ابتدا `paymentVerified` را بررسی کنید و سپس بر اساس `purpose` و `resultPath` مسیر بعدی را انتخاب کنید.
- هیچ‌وقت `Authority` یا `paymentToken` را در LocalStorage ذخیره نکنید.
- در صورت نبودن `resultPath` برای پرداخت رزرو، از مسیر جدید حدس‌زده‌شده استفاده نکنید؛ نتیجه رزرو را با `bookingIds` نمایش دهید.

## ۷. چک‌لیست تست فرانت‌اند

- نمایش دسته‌های عمومی
- نمایش دسته اختصاصی مالک
- جلوگیری از انتخاب دسته غیرفعال برای هزینه جدید
- ثبت هزینه با مبلغ ریالی
- رد هزینه با مبلغ صفر یا منفی
- رد اتصال هزینه به دسته مالک دیگر
- ویرایش و حذف هزینه مالک خود کاربر
- رد حذف دسته دارای سابقه
- مشاهده پاسخ موفق اشتراک Worker
- مشاهده پاسخ موفق اشتراک Workshop
- مشاهده پاسخ موفق پرداخت چند رزرو
- مدیریت پرداخت ناموفق
- Refresh صفحه کال‌بک بدون ایجاد پرداخت تکراری
- بررسی اشتراک فعال برای Worker و Workshop
- نمایش ظرفیت کل، مصرف‌شده و باقی‌مانده اشتراک
- نمایش حالت تسویه `Business` و `Separate`
- نمایش درصد سهم متخصص و مبلغ نهایی هر طرف
